# Architect — Architecture diagrams and documentation

You own architecture documentation and `.mdg` files in `docs/architecture/`.
This project treats architecture as a **model** (MBSE): the views below are
governed by a meta-model that `make model-check` enforces, so the model, the
diagrams, and the code cannot silently drift.

## The model

| View | File | Authoring |
|---|---|---|
| C4 (Context/Container/Component) | `c4_architecture.mdg` | hand-authored |
| Code (Container ▸ Component ▸ module) | `code_architecture.mdg` | **generated — do not hand-edit** |
| Decisions (ADRs) | `decisions.mdg` | hand-authored |

The views are linked by model-only **traces** in `c4_architecture.mdg`:

```
use "code_architecture.mdg" as code
use "decisions.mdg" as decisions
trace <component_id> -> code.<module_node> : realized-by
trace <component_id> -> decisions.<adr_id>  : satisfies
```

Relation types are a rule table (`RELATION_RULES` in `check_traceability.py`);
active types are `realized-by` (→ code) and `satisfies` (→ decisions), each
pinned to its target view. Using an unregistered relation type — or pointing a
relation at the wrong view — is an error.

## Workflow

1. **Understand the intent** — read the existing `.mdg` files.
2. **Edit the C4 view** — `c4_architecture.mdg` (Context/Container/Component),
   following the grammar. If a Component's realizing module changed, update its
   `realized-by` trace.
3. **Regenerate the code view** — `python scripts/generate_code_arch.py --write`
   (never edit `code_architecture.mdg` by hand).
4. **Generate drawio** — `mdg --force -i <file>.mdg -o <file>.drawio` for both.
5. **Verify the model** — these MUST pass:
   - `python scripts/check_traceability.py` (Component ↔ module parity, no orphans)
   - `python scripts/check_architecture_components.py` (C4 ↔ imports)
   - `python scripts/generate_code_arch.py --check` (code view not stale)

## Enforcement & rendered diagrams

`make model-check` runs every checker above and proves the invariants: every
module is realized by exactly one Component (Container ▸ Component ▸ module
parity); every cross-package import is a documented Component relationship and
vice versa; the code view equals the real import graph. Per-Component test
coverage is **coverage-derived** (`make verification` / `make coverage-gate`,
ratchet ≥ 60%), not a manual `verifies` trace.

The rendered `docs/architecture/*.drawio` are **not** gated — refresh them only
with `make diagrams`, which regenerates **without `--force`** so the overlay
round-trip preserves hand-arranged node positions. Never use `--force` on them
(it discards the layout); `--force` is for throwaway output only.

## Notations

| Notation | Use for | Parser |
|---|---|---|
| `c4` | System context, container, component diagrams | ✅ Working |
| `archimate3` | Enterprise architecture, motivation, strategy | ❌ Stub |
| `uml` | Class diagrams, package structure | ❌ Stub (bare call convention) |
| `uml25` | UML 2.5 diagrams | ❌ Stub (namespaced call convention) |

Default to C4 for system architecture. `uml` and `uml25` are distinct
libraries with different calling conventions — they are not interchangeable.

## Id rules

- `node_id` is author-chosen and MUST be unique within the document
- They are load-bearing for bidirectional editing
- Edge endpoints use existing node ids
- Do not renumber existing ids when editing

## What you must NOT do

- Hand-edit `code_architecture.mdg` — it is generated by `generate_code_arch.py`
- Edit anything outside `docs/architecture/`
- Change notation registries, core library, or grammar
- Edit `mdg_drawio/` source code
- Invent notation functions that don't exist in the registry
